Overview. This work raises vulnerability-disclosure and dual-use considerations. It involves no human subjects and does not test any third-party live system. We address each CFP category below.

Vulnerability Disclosure. DeFenzz found 111 previously unknown silent defense bugs, 58 in GCC and 53 in LLVM/Clang. Before submission, we reported all 111 bugs to the upstream maintainers through their official public trackers (GCC Bugzilla and LLVM GitHub Issues). We used public trackers because this follows both projects' security policies. GCC's SECURITY.txt states that a failure of hardening features such as -fstack-protector or _FORTIFY_SOURCE to work in all situations is not a vulnerability in itself. LLVM's security policy treats most miscompilations as regular bugs. None of our bugs is exploitable on its own: each one weakens a mitigation only for specific code patterns, and an attacker still needs a separate memory-safety bug in the application. Each report contains a minimal C/C++ test case, the compiler flags, the emitted assembly or runtime output, and a root-cause analysis. No report contains an exploit against real software. As of submission, maintainers have officially confirmed 30 bugs (18 GCC, 12 LLVM). Of these, 11 are fixed in mainline (9 GCC, 2 LLVM), 1 is partially fixed, and several GCC fixes have been backported to release branches. Maintainers have also tagged 5 more reports as wrong-code or miscompilation. The remaining 76 reports have been filed and are still awaiting maintainer triage or patch review. We continue to track all open reports, answer maintainer questions, and help test patches. Because every bug has already been reported, disclosure is complete well before the rebuttal deadline. To keep the review double-blind, the manuscript and the artifact omit upstream bug IDs, reporter accounts, and full CVE numbers.

Effort Imposed on Maintainers. Our reports take up the time of open-source maintainers. To keep this cost low, an author reproduced every candidate and reviewed every report before filing it. We also searched both trackers for duplicates and reduced each test case to a minimal reproducer. We audited 131 candidate findings and did not file candidates that lacked clear documentation support or duplicated an existing ticket. When maintainers disputed a report or showed that the behavior was intended, we excluded that report from the 111 bugs counted in the paper.

Human Subjects and Live Systems. This study involves no human subjects, user data, or personally identifiable information. We build GCC and LLVM from public source releases and run all test programs in isolated rootless containers on one server under our control. No IRB review was therefore required. Filing the bug reports described above was our only interaction with outside parties.

New Tool and Dual-Use Risk. DeFenzz is a defensive testing tool. It checks compiled binaries against documented security rules and outputs minimal compiler test cases with pass or fail verdicts. It does not generate exploits or target deployed software. An attacker could still use DeFenzz or our bug list to learn where a compiler mitigation is weaker than expected. We consider this risk low. Exploiting any of these bugs still requires a separate memory-safety or control-flow bug in an application built with the affected code pattern and flags. All 111 bugs are already public on the upstream trackers, and the anonymized bug catalog in our artifact adds no information beyond those reports. Compiler maintainers gain the most from the tool, because they can run it on every release before users ship affected binaries.

Novel Attacks. We do not propose new attack techniques. Our case studies explain how a mitigation fails in the compiler output and what causes the failure. The fix for each bug is an upstream compiler patch. For bugs that are not fixed yet, maintainers already know about them and can prioritize fixes, and downstream users can follow the public reports and update once patches land.

Benefits and Risks. Silent defense bugs give developers and users a false sense of security: a binary built with hardening flags looks protected but is not. Finding and fixing these bugs in GCC and LLVM, the two most widely used C/C++ compilers, protects a large number of downstream programs. We judge that this benefit clearly outweighs the remaining risk.
